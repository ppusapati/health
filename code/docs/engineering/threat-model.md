# Threat model: Wave-0 platform foundation

Covers SRS-SEC-007. Scope is what Wave 0 actually built: the ConnectRPC
boundary, the tenant and identity model, the outbox, the workflow and rules
engines, the hospital edge node, and the deployment substrate. Clinical domains
arrive in Wave 1 and get their own models — the requirement is per high-risk
domain, not one document forever.

Method is STRIDE per trust boundary, because the boundaries are what this
architecture is made of. Each finding ends in one of three places: a control
already in the code (cited by file), an action in
`security/threat-model-actions.yaml` with an owner and a due date, or an
explicitly accepted risk. Nothing ends in prose alone; `tools/security`
enforces that the action register is complete and that nothing is overdue.

## Assets, in the order an attacker would want them

1. **PHI at rest** — the clinical record. Everything else is a route to it.
2. **Tenant isolation** — one hospital reading another's records is both a
   breach and a contractual failure, and it scales: a defect here exposes every
   tenant at once, not one record.
3. **The audit and security event chain** — an attacker who can edit history
   converts a detected breach into an undetected one.
4. **Credentials and keys** — database credentials, edge node certificates,
   KMS aliases.
5. **Availability** — a hospital that cannot reach its EMR falls back to paper,
   which is a patient-safety event, not an inconvenience.

## Trust boundaries

```
   Internet ──1──▶ Ingress ──2──▶ core (ConnectRPC) ──3──▶ PostgreSQL
                                      │
                                      ├──4──▶ outbox → broker (ADR-005 open)
                                      ├──5──▶ object store
                                      └──6──▶ OTel collector

   Hospital ward ──7──▶ edge node ──8──▶ cloud ingest
```

### Boundary 1–2: Internet to the RPC surface

**Spoofing — a caller asserts an identity.**
Only `internal/platform/transport` and `internal/edge/cloudstore` may mint a
session, and both do it by verifying a credential. This is enforced as an
architecture fitness test (`TestOnlyTransportMintsSessions`), so a handler that
constructs a session from a request field fails the build rather than review.

**Tampering — a client widens its own scope through headers.**
This was a real defect, found during the Wave-0 audit and fixed: the facility
and purpose-of-use headers overwrote the verified session rather than narrowing
it. `Session.PermitsFacility` and `PermitsPurpose` now bound both, and
`header_scope_test.go` holds the guards in place. The lesson generalises —
*any* client-supplied view selector must be checked against the credential, not
merely recorded — and it is why the fitness suite asserts the guards exist at
all, not just that they currently pass.

**Repudiation.** Every mutating call writes an audit record inside the same
transaction as the change (`internal/platform/audit`), so a successful write
cannot exist without its audit row.

**Information disclosure — cross-tenant probing.**
A cross-tenant read returns `NOT_FOUND`, never `PERMISSION_DENIED`: the second
confirms the identifier exists. `milestone2_isolation_test.go` asserts the
distinction at the RPC, repository, outbox and audit layers.

**Denial of service.** Two-stage rate limiting: by peer address before
authentication, by subject after (`internal/platform/transport/ratelimit.go`).
The first stage has to come first, or an unauthenticated flood is never
attributable to a bucket at all.

> **Action TM-0003**: the unauthenticated bucket is per-process. A multi-replica
> deployment therefore permits *n* × the intended rate. Acceptable at Wave-0
> replica counts; needs a shared counter before production scale.

### Boundary 3: service to database

**Tampering in transit.** `ValidateDatabaseDSN` refuses any `sslmode` that does
not authenticate the server, `require` included — it encrypts but accepts any
certificate, so an attacker who can answer for the database reads everything.

**Elevation — SQL injection.** All production SQL is generated by sqlc from
`.sql` files; `internal/platform/sqlcgen` may only be imported by adapter
packages (FIT-02). A handler cannot reach a query builder.

**Elevation — a repository called without tenant scope.**
`authctx.TenantScope` has an unexported field and no public constructor
(ADR-001). A repository method cannot be called without a scope derived from a
verified session, so FIT-03 is a compile error rather than a review convention.
This is the single most load-bearing decision in the codebase.

**Information disclosure — cross-schema reads.** Each bounded context owns its
schema and only its own adapter may reference it (`schemaOwners` in
`tools/fitness`).

### Boundary 4: outbox and broker

**Tampering — events published for a tenant the producer cannot act as.**
The outbox row is written in the same transaction as the state change, so an
event with no corresponding change cannot exist. The tenant on the envelope
comes from the scope, not from the payload.

**Repudiation and replay.** Delivery is at-least-once with consumer-side
dedup on the envelope id.

> **Action TM-0005**: ADR-005 (broker selection) is open. The seam is one
> interface, but the broker's own authorization model — who may publish to a
> tenant's topic — is not yet designed. Must close before any cross-tenant
> consumer exists.

### Boundary 5: object store

Bulk export is the high-risk path: it is the one legitimate way a large volume
of PHI leaves the system. `internal/security/domain/export.go` requires a
justification, a step-up authentication reference, and approval by someone
other than the requester; the download grant expires; the completed object
carries a SHA-256 that the manifest records.

> **Action TM-0007**: object-store adapters for export are not yet written, so
> the domain rules above are not yet reachable from the RPC surface. No export
> path exists today, which is safe — but the gap must not be closed by writing
> the adapter without the approval flow.

### Boundary 6: telemetry

**Information disclosure — PHI in a span or a log.**
Structured logging carries identifiers, never clinical values
(`internal/platform/obs`). The risk is that this is a convention.

> **Action TM-0009**: add a PHI-shaped-value detector over log and span
> attribute keys, so a new field named `patient_name` fails a test rather than
> reaching a collector.

### Boundary 7–8: hospital edge

**Spoofing — an attacker enrols a node.** Enrollment tokens are single-use and
stored hashed. Ingest authenticates the node by certificate fingerprint
(`AuthenticateNode`); the node's tenant comes from the enrolment record, so a
node cannot ingest for another tenant.

**Tampering — command injection into a label printer.** ZPL control characters
in a field would let a crafted patient name emit printer commands; `escapeZPL`
neutralises them. Found by review, not by a test failure — which is the reason
the escaping now has its own tests.

**Repudiation and duplication.** Ingest is idempotent on
`(node, operation id)`, so a queue replayed after a WAN outage produces no
duplicate clinical effect.

**Availability — WAN loss.** Store-and-forward SQLite queue; the ward keeps
working and reconciles on recovery. This is the tested scenario in
`internal/edge`.

### Deployment substrate

Default-deny NetworkPolicy, restricted Pod Security, distroless image with no
shell running as UID 65532, secrets from the managed store only. Each of these
is asserted by `tools/infra` rather than by convention, including a check that
an overlay patch cannot weaken a base security control — the realistic attack
here is not an intruder but a rushed patch that adds `privileged: true` to make
a debug container work.

## What this model deliberately does not cover

- **Clinical domain logic.** No patient, encounter or order model exists yet.
- **The identity provider.** ADR-008 is open; only the development verifier
  exists, and `AUTH_MODE` has no default so it cannot be reached by
  configuration drift. The model of the real IdP arrives with the decision.
- **Insider threat by a platform operator.** Someone with cluster admin and KMS
  access can read PHI. The controls against this are organisational
  (separation of duties, break-glass review) and partly built —
  `internal/security/domain/emergencyaccess.go` — but the operator path is not
  yet instrumented.

> **Action TM-0011**: extend the security event chain to cover operator access
> to production data stores, not only application-level privileged changes.

## Review trigger

Re-run this model when any of the following happens, per SRS-SEC-007:

- a new bounded context handles PHI (every Wave-1 domain qualifies)
- a new external integration is added (broker, IdP, payer, lab, device)
- an ADR closes in a way that changes a trust boundary
- a penetration test finds something this model did not anticipate — the miss
  is itself a finding about the model
